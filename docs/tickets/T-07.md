### Rules (same as T-05 / T-06)

- `"use client"`. Actions return `{ ok, data } | { ok: false, error: { code, message } }`
  and call `refresh()` on the server, so after success the page re-renders with new props.
  Don't refetch.
- Errors: forms and dialogs show them inline (`<p role="alert" className="text-sm text-destructive">`);
  row actions use `toast.error(message)` from `sonner`. Success is silent. The server's
  messages are written for users ("A project needs at least one Done status…"), so show
  them as they are.
- **Base UI, not Radix:** `render={<Button … />}` instead of `asChild`; `Select` needs
  `items`; `AlertDialogAction` doesn't close by itself (control `open`); `DropdownMenuLabel`
  goes inside `DropdownMenuGroup`.
- **Drag and drop:** copy the approach in `project-tree.tsx` exactly. That means `@dnd-kit/core`
  and `@dnd-kit/sortable` only (no `@dnd-kit/utilities`), a **`DndContext id={useId()}`**
  (without it, hydration fails), and a grip handle carrying `{...attributes} {...listeners}`.
  Keep the order optimistic: `items` state reset from props during render when the prop
  changes identity. On drop, call the reorder action with
  `beforeId: next[i-1]?.id ?? null, afterId: next[i+1]?.id ?? null`. On failure, reset
  and `toast.error`.
- Look (9.8): sections are `<section className="space-y-4">` with `<h2 className="text-base font-semibold">`
  plus an optional muted intro. Rows are `divide-y rounded-lg border`, each
  `flex items-center gap-3 px-4 py-2.5`, and inline inputs are `h-8`.

### 1. `ProjectDetailsForm({ projectId, name, color })` — any member

Section "Project". A name `Input` (`maxLength={80}`) plus a "Save" button, disabled until
the trimmed value changes. It validates with `updateProjectSchema` and calls
`updateProjectAction({ projectId, name })`, showing errors inline. Below it, "Color": a row of
the 10 `PROJECT_COLORS` swatches (`size-6 rounded-full`, `aria-label`, `aria-pressed`,
selected = `ring-2 ring-offset-2 ring-ring`). Clicking a swatch saves immediately with
`updateProjectAction({ projectId, color })` and shows `toast.error` on failure.

### 2. `StatusesEditor({ projectId, statuses, canEdit })`

Section "Statuses", intro "Statuses belong to this project. It always keeps at least one
To do and one Done status." `statuses` is already in order; each has `taskCount`.

**When `canEdit` is false (Members):** read-only rows showing a color dot (`size-2.5 rounded-full`),
the name, a category `Badge variant="secondary"` (labels from `STATUS_CATEGORY_LABELS`), and
muted "N tasks". Under the list, a muted "Only Owners and Admins can edit statuses."

**When `canEdit` is true**, each row, left to right:
- grip handle (drag to reorder → `reorderStatusAction({ statusId, beforeId, afterId })`);
- **color**: a small round swatch button (`size-4 rounded-full`, `aria-label="Color"`) opening a
  `DropdownMenu` of `STATUS_COLORS` (swatch + name, `Check` on the current one) →
  `updateStatusAction({ statusId, color })`;
- **name**: text that turns into an `Input` on click. Enter or blur saves if it changed,
  Esc cancels. It validates with `updateStatusSchema` and calls `updateStatusAction({ statusId, name })`,
  with `toast.error` on failure;
- **category**: `Select` (`w-28`) with To do / Active / Done (values `TODO`/`ACTIVE`/`DONE`,
  `items` from `STATUS_CATEGORY_LABELS`). Control its value **from the prop**, calling
  `updateStatusAction({ statusId, category })` on change. On failure use `toast.error`; the
  prop is unchanged, so the select snaps back;
- muted "N tasks" (`text-xs`, "1 task" singular);
- **delete**: ghost `icon-sm` button with `Trash2`, `aria-label="Delete <name>"`, opening the dialog below.

**Delete dialog** (controlled `AlertDialog`): title "Delete <name>?". Description: if
`taskCount > 0`, "Its N task(s) will move to the status you pick."; otherwise "No tasks use
this status." Show a "Move tasks to" `Label` + `Select` of the *other* statuses (with `items`),
defaulting to the first other status of the **same category**, or else the first other status.
Show it even when `taskCount` is 0, because the server requires a replacement. Buttons: Cancel,
and a destructive "Delete" → `deleteStatusAction({ statusId, replacementStatusId })`. On
error, show the message **inline in the dialog** and keep it open. On success, close it.

**Add status** (below the rows): a form row with `Input` (placeholder "New status",
`maxLength={40}`), a category `Select` (default `ACTIVE`), and an "Add" button. Color defaults to
`STATUS_COLORS[0].value`. It validates with `createStatusSchema` and calls
`createStatusAction({ projectId, name, color, category })`, showing errors inline. On success,
clear the name.

### 3. `ListsEditor({ spaceId, projectId, lists, canDelete })`

Section "Lists", intro "A project always has at least one list." Rows:
- grip handle (drag → `reorderListAction({ listId, beforeId, afterId })`), for everyone;
- `Hash` icon, then the **name**, inline-editable by everyone (same behaviour as status names),
  → `updateListAction({ listId, name })`;
- muted "N tasks";
- **delete** (only if `canDelete`): a `Trash2` ghost button. When `lists.length === 1` it's
  `disabled` with `title="A project needs at least one list"`.

**Delete dialog:** title "Delete <name>?". Description: "Its N task(s), with their subtasks,
will move to the list you pick. Tasks that were only linked here stay in their own lists."
(If N is 0: "It has no tasks.") A "Move tasks to" `Select` of the *other* lists, defaulting to
the first. Buttons: Cancel, and a destructive "Delete" → `deleteListAction({ listId, targetListId })`.
Errors show inline; close on success.

**Add list** (below the rows, everyone): `Input` (placeholder "New list", `maxLength={80}`) plus
an "Add" button → `createListAction({ projectId, name })`, validated with `createListSchema`,
errors inline, clear on success.

(`spaceId` is available if you need to build list URLs; the subtask display setting is **not**
edited here, it belongs to the list view in T-09/T-12.)
